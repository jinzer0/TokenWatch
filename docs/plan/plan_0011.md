# TokenWatch Phase 1 — Audit & Provenance

## 역할

당신은 기존 오픈소스 프로젝트 **TokenWatch**를 직접 수정하는 senior TypeScript engineer다.

Repository:

`https://github.com/jinzer0/TokenWatch`

이번 작업의 목표는 새 기능을 이것저것 추가하는 것이 아니다.

**TokenWatch가 수집하고 표시하는 usage/cost 데이터의 출처, 품질, coverage, pricing 신뢰도를 사용자가 점검할 수 있는 `audit` 기능을 추가하는 것**이 이번 Phase의 유일한 목표다.

현재 저장소의 코드, README, DESIGN, 테스트를 먼저 읽고 실제 구조를 source of truth로 사용한다. 이 프롬프트와 현재 코드가 충돌할 경우 기존 privacy/security contract와 실제 코드 구조를 우선한다.

---

# 1. 핵심 목표

새 CLI 명령을 추가한다.

```bash
tokenwatch audit
tokenwatch audit --json
tokenwatch audit --window 7d
tokenwatch audit --window 30d
tokenwatch audit --source codex
tokenwatch audit --source codex --source claude
tokenwatch audit --source-name local
```

이 명령은 다음 질문에 답해야 한다.

1. 어떤 source가 실제 token usage parser이고 어떤 source가 unsupported/status-only인가?
2. 각 parser는 어떤 형태의 token accounting contract를 사용하는가?
3. 최근 scan에서 insert/duplicate/conflict/reject/error가 얼마나 발생했는가?
4. 저장된 event 중 가격을 알고 있는 비율과 모르는 비율은 얼마인가?
5. pricing source와 pricing confidence는 어떻게 분포하는가?
6. session attribution이 가능한 event와 불가능한 event 비율은 얼마인가?
7. 현재 데이터에서 어떤 부분을 신뢰할 수 있고 어떤 부분은 unknown인가?
8. audit 결과 역시 TokenWatch의 privacy boundary를 지키고 있는가?

`audit`은 billing correctness를 보증하는 기능이 아니다.

데이터 provenance와 coverage를 설명하는 diagnostics 기능이다.

---

# 2. 절대 지켜야 할 Privacy Boundary

TokenWatch의 기존 privacy 철학을 절대로 약화하지 않는다.

다음 값은 DB, report, JSON, terminal output, logs, exception output에 새로 노출하거나 저장하지 않는다.

- prompt
- response
- message content
- source code
- API key
- OAuth token
- credentials
- raw file path
- workspace path
- raw session ID
- raw provider response
- raw record
- SQL payload
- stack trace
- arbitrary metadata dump
- shell command text
- tool arguments

기존 hashed identifier와 explicit safe label만 사용할 수 있다.

새로운 audit 기능 때문에 generic metadata storage를 넓히지 않는다.

현재 allowlist 기반 metadata 정책을 유지한다.

Privacy 검사를 우회하거나 느슨하게 만들지 않는다.

# 4. Parser Accounting Mode 추가

각 parser가 token count를 어떤 방식으로 얻는지를 source-level metadata로 표현한다.

기존 parser registry metadata 구조에 맞춰 구현하되 개념적으로 다음과 같은 bounded enum이 필요하다.

예시:

```ts
type TokenAccountingMode = 'direct' | 'delta' | 'aggregate' | 'telemetry' | 'mixed' | 'unsupported';
```

정확한 이름은 현재 code style에 맞게 조정할 수 있다.

각 의미는 명확해야 한다.

### direct

로컬 artifact가 해당 event/message 수준의 usage token count를 직접 제공한다.

### delta

artifact에 cumulative counter가 있고 parser가 이전 값과의 차이를 계산한다.

예:

Codex cumulative token usage delta.

### aggregate

artifact가 session 또는 aggregate usage total만 제공하고 TokenWatch가 이를 aggregate event로 변환한다.

### telemetry

OpenTelemetry와 같은 structured usage attribute가 token 값을 제공한다.

### mixed

한 source parser 안에서 여러 안정적인 accounting contract가 사용된다.

### unsupported

실제 non-zero usage artifact contract가 확인되지 않은 status parser.

---

## 매우 중요

각 parser를 이름만 보고 추측해서 분류하지 않는다.

실제 parser implementation과 fixture를 읽고 근거가 확인되는 경우에만 mode를 지정한다.

분류가 애매하다면 `mixed` 또는 보수적인 값을 사용한다.

README에 없는 사실을 새로 만들어내지 않는다.

`direct`를 "billing exact"라는 뜻으로 사용하면 안 된다.

Accounting mode는 **token count를 어떻게 얻었는가**만 설명한다.

# 5. Audit Report Contract

새로운 versioned 또는 strict audit report contract를 만든다.

현재 프로젝트의 report contract 패턴을 따른다.

JSON top-level 구조는 개념적으로 다음 정보를 포함해야 한다.

```ts
{
  kind: 'audit',
  window: ...,
  filters: ...,

  totals: {
    events,
    tokens,
    knownCostEvents,
    unknownCostEvents,
    knownCostTokens,
    unknownCostTokens
  },

  pricingCoverage: {
    knownEvents,
    unknownEvents,
    coverageRatio,
    bySource: [...],
    byConfidence: [...]
  },

  sessionCoverage: {
    withSession,
    withoutSession,
    coverageRatio
  },

  sourceContracts: [
    {
      source,
      displayName,
      supportStatus,
      accountingMode
    }
  ],

  scanHealth: {
    runs,
    discoveredFiles,
    parsedEvents,
    insertedEvents,
    duplicateEvents,
    conflictEvents,
    skippedRecords,
    rejectedRecords,
    errorRecords,
    warningCodes: [...]
  },

  warnings: [...],

  privacy: {
    sanitized: true
  }
}
```

위 shape를 문자 그대로 복사할 필요는 없다.

기존 TokenWatch DTO/report naming convention에 맞게 설계한다.

하지만 다음 원칙은 반드시 유지한다.

- strict schema validation
- predictable JSON
- nullable/unknown 값을 억지로 0으로 변환하지 않음
- deterministic ordering
- sanitized output only
- raw data 없음

# 6. Pricing Coverage

현재 저장된 event의 다음 필드를 활용한다.

- `estimatedCostUsd`
- `pricingSource`
- `pricingConfidence`
- `normalizedProvider`
- `normalizedModel`

audit은 최소한 다음을 표시해야 한다.

- cost known event count
- cost unknown event count
- known/unknown token count
- event 기준 pricing coverage ratio
- token 기준 pricing coverage ratio
- pricing source distribution
- pricing confidence distribution

가격이 unknown인 event를 다음처럼 처리하면 안 된다.

```text
$0.00
free
zero cost
```

반드시 `unknown` 의미를 유지한다.

---

# 7. Scan Health

기존 `scan_runs`를 활용한다.

선택된 audit window/filter에 해당하는 범위에서 가능한 경우 다음 값을 집계한다.

- scan run count
- discovered files
- parsed events
- inserted events
- duplicate events
- conflict events
- skipped records
- rejected records
- error records
- warning code distribution
- failed scan count

raw path나 raw parser exception은 출력하지 않는다.

warning/error는 기존 sanitized code만 사용한다.

---

# 8. Source Contract Report

24개 registered source를 모두 audit report에서 확인할 수 있어야 한다.

각 source에 최소한 다음 정보를 제공한다.

- source key
- safe display name
- `real_parser` 또는 `unsupported_status_parser`
- token accounting mode

필터가 주어진 경우 동작을 명확하게 한다.

예를 들어:

```bash
tokenwatch audit --source codex
```

를 실행하면 source contract와 usage aggregation이 모두 `codex` 기준으로 제한되어야 한다.

복수 `--source`는 현재 TokenWatch convention과 동일한 OR semantics를 사용한다.

---

# 9. Session Coverage

기존 `sessionIdHash`를 사용해서 다음을 계산한다.

- session hash가 존재하는 event 수
- session hash가 없는 event 수
- session coverage ratio

raw session identifier는 절대 출력하지 않는다.

Audit Phase에서는 session hash 목록 자체도 출력할 필요가 없다.

aggregate count만 제공한다.

# 12. Window Semantics

가능하다면 기존 report/window parsing utility를 재사용한다.

최소 지원:

```bash
--window 7d
--window 30d
```

기본 window는 현재 TokenWatch의 기존 analytics/report semantics를 조사해서 가장 일관적인 값으로 결정한다.

새로운 의미를 임의로 만들지 않는다.

Source contract 자체는 시간과 무관한 registry metadata다.

Usage/pricing/session/scan health만 window 영향을 받는다.

이 차이를 report에서 명확히 유지한다.

---

# 13. Filtering

최소 다음 filter를 지원한다.

```bash
--source <source>
--source-name <label>
```

반복 option semantics는 기존 TokenWatch 명령과 동일하게 한다.

- 같은 dimension 안에서는 OR
- 서로 다른 dimension 사이에서는 AND

예:

```bash
tokenwatch audit \
  --source codex \
  --source claude \
  --source-name workstation
```

는:

```text
(source == codex OR source == claude)
AND
sourceName == workstation
```

의미여야 한다.

# 14. Database Migration

가능하면 이번 Phase에서 schema migration을 만들지 않는다.

Audit은 현재 존재하는 다음 정보를 우선 사용한다.

- parser registry metadata
- usage_events
- scan_runs
- pricing fields
- sessionIdHash

Accounting mode는 source-level parser metadata로 표현한다.

event마다 redundant accounting mode를 저장하지 않는다.

현재 데이터로 구현이 불가능한 명확한 이유가 있을 때만 migration을 고려한다.

migration을 추가할 경우 반드시 이유를 문서화한다.

- session coverage가 정확하다.
- scan health aggregate가 정확하다.
- source/sourceName filtering이 정확하다.

- `kind`가 audit이다.
- strict schema validation을 통과한다.
- deterministic output이다.
- `privacy.sanitized === true`

# 16. Documentation

예:

```bash
tokenwatch audit

```

문서에서 다음 사항을 명시한다.

- audit은 billing verification이 아니다.

- pricing은 local planning estimate다.
- unknown pricing은 unknown으로 유지된다.
- raw prompts/responses/paths/session IDs는 audit에 포함되지 않는다.

필요하다면 DESIGN 문서도 업데이트한다.

기존 문서와 중복되거나 서로 모순되는 설명을 만들지 않는다.
